**Boot 2 is GO — with one correction to how I first framed it.**

**The warm-reboot shortcut is not safe as stated.** "The unlocked state survives a warm reboot" came from your observation — but it is an inference (persistent rejection across the reboot), not a register readback, and on your box it cannot be checked directly (the 6.12 sysfs-mmap block). The general expectation in our records is the opposite: S5/shutdown clears the volatile state (#188), a Turing FLR clears the FEAT block entirely, and the per-boot replay doctrine exists precisely because reboot-class resets wash it on most machines (your own Nov 3 locked control inits fine, which makes a washed state look exactly like "driver fixed" from acceptance alone). On a GTX 1650 specifically — no tensor cores, no register readback — "580.142 + warm reboot + init passes" cannot distinguish "driver accepts the unlocked state" from "state washed + driver accepts factory".

**So the decisive form of Boot 2 is: swap the driver to 580.142 AND run a fresh USB transaction boot** (unlock → handoff → init) — one cold boot, unambiguous by construction: the state is freshly unlocked, so an init failure implicates the driver axis and a pass means 580.142 accepts the TU117 unlocked handoff.

**If you want the warm-reboot survival measured as its own datum first**, a reboot-only probe works and costs nothing: reboot without swapping anything — init fails again with the same tuple = the state survived your platform's reboot (your box would be an outlier worth recording); init succeeds = it washed (matches the general expectation). Either result is useful; it is one reboot with no driver swap.

**On the mmap EINVAL — corrected attribution.** That is not a known mainline behavior: the v6.11→v6.12 `pci-sysfs.c` window added no mmap restriction, and our control box (Ubuntu 24.04.5, kernel **7.0.0-43-generic**, Secure Boot off, root) reads BAR0 through the same sysfs mmap just fine — including through the unlocked state, with `tools/diag-unlock.py` reading `FEAT_PLM=0xffffffff / SS0=0x88888888 / SS1=0x8` on two 3090s. So the refusal is specific to your box, not the kernel version. Three one-minute checks will pin it:

```bash
cat /sys/kernel/security/lockdown    # not "none" = lockdown LSM active: BAR access is denied to ROOT under Secure Boot / lockdown= (2019 v5.4 behavior, direction-agnostic - reads die with the map)
mokutil --sb-state                   # Secure Boot state; the usual trigger for lockdown
strace -e mmap python3 tools/diag-unlock.py --bdf 0000:01:00.0 2>&1 | grep mmap   # exact errno + kernel log line
```

If lockdown turns out active (Secure Boot re-enabled after the unlock boots — which the workflow makes easy to do accidentally), flipping it off should restore the sysfs path — the `diag-unlock.py` poke capability (`--target-offset/--value`, same as the Windows 0.8.9 bench) then works on your box too, and the #286-style SS/PLM scan becomes available on the Linux side. If the cause is something else entirely, paste the three outputs and we will take it from there — until then your plan stands on cold boots alone, which is unaffected.
