## Supplementary measurements

The records below fill in the experimental conditions referenced by the compatibility matrix; units are TFLOPS, and the values represent only the corresponding platform and method.

### RTX 4060 Ti 8GB · AD106 `2803` (first 8 GB `2803` data point)

Source: [PR #87](https://github.com/physicsdolphin/nv-uefi-unlocker/pull/87), reporter @fujiaghost789-glitch. ASUS PRIME B760M-F D4 (Intel B760/AMI), 8 GB `2803` — all prior `2803` reports were 16 GB. Unlock readback pass (PLM open, SS0/SS1=`0x88888888`/`0x8`, READOUT_1=0); cuBLAS 4096³ median of three runs: FP16 45.59→77.36 (+69.7%), BF16 45.64→77.74 (+70.3%), TF32 20.06→41.91 (+108.9%), FP32 control is noise. **Bundled fix**: with VT-d off, this machine's upstream bridge `8086:a70d` starts with BME cleared, exposing a defect where the `BridgeMaster` guard dropped early inside the else block (booter `0x89` family) — the fix landed in main with PR #87 (ae7b128) and is a no-op for existing verification setups where BME is already enabled.

### RTX 4070 · AD103 `2709`

Source: [#8](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/8). B760 desktop, dGPU direct; four-write readback pass, selectors retained after FLR. System-side sm_89 MMA microbenchmark: FP16 ~61→123.91, BF16 118.90, FP8 243.55; reported multiples all ~2.0×.

### RTX 3080 LHR · GA102 `2216`

Source: [#15](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/15). B550, no iGPU, single display card. FP16 GEMM 8192 57.72→94.0–96.9 (+63~68%), BF16 +74~79%, TF32 +52~67%, ComfyUI SDXL +28.8%; per-SM rate in the same band as the 3090 Ti reference card.

### RTX 2060 Super · TU106 `1f06`

Source: [#12](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/12), reporter @vadash, tested on v0.2.0. ### Independent corroboration: X99 + CSM-on → Code 12 (upstream community reproduction of the #88/#61 findings)

Source: [Zagitta/gpu-unlock issue #28 comments](https://github.com/Zagitta/gpu-unlock/issues/28) (user 3615074213, 2026-10-31). Jingsha X99-8D3 (AMI 5.11) + Windows 11: **with CSM on, the unlock transaction is fully green but Windows lands Code 12 / 0xC0000018; with CSM off, the driver loads normally** — independently consistent with this repo's [#88](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/88) (A4G/ReBAR not hard prerequisites; CSM off = recommended for the display chain) and [#61](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/61) (Code 12 law: handoff console-ownership chain failing on both counts → Code 12, independent of unlock/family/topology). The same comment adds board-level ceiling corroboration: after unlock, ~1024 FLOP/SM/clk on an 0x151E board vs ~846 on an 0x300 board, in line with per-board power-delivery/BIOS differences.

## Community no-USB tool records (unofficial, not endorsed)

§1.4 is absolute for project deliverables (decision record in [#73](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/73)): this project does not ship resident-boot-entry installers and provides no official tutorials. The community approaches below are recorded for existence only — unofficial, not endorsed, no compatibility promised; the risk model of a resident boot entry (automatic firmware-transaction replay on every power-up, and a black screen requiring recovery media or the firmware menu if the chain-load fails) is borne by the user:

- [#33 reporter's scripts](https://github.com/chungtair/rtx4060ti-auto-unlock): 300 MB FAT32 partition on a data drive + a `{fwbootmgr}` firmware boot entry, tested on AD106/MSI B550 (row #33 above; note the B550 ignores the boot order written by Windows — you must set Boot Option #1 manually in BIOS).
- [#29 reporter's ESP experiment](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/29) (tested on GA102/Z490, row #29 above): putting the unlocker on the system ESP is feasible, but capacity is a hard constraint — this machine's ESP was only 100 MB (69.1 MiB initially free) while the ga102 payload needs 80.7 MiB (`fwimage_ga102.bin` alone is 80.3 MiB), leaving it 11.6 MiB short of the full package; the reporter resized with a PE stick + diskgenius, rebuilt the boot chain and got it working, also self-shortening the confirmation countdown to 2 s. Consistent with the #73 downstream tool's "reject ESP" design trade-off: the ESP route has no headroom for payload size, and a dedicated partition is more robust.
- [The #73 proposer's downstream tool](https://github.com/Catnip202X/nv-uefi-unlocker/tree/downstream): `downstream/install-partition.ps1`, install/uninstall on a dedicated FAT32 partition (per-file SHA-256 verification, manifest written before the boot entry, rejects ESP/removable disks/partial asset sets, `-AllowArmed` gates auto-confirmation). The author honestly states the script was never actually executed — the first real run is the test.
