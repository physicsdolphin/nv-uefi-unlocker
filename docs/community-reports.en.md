ASUS PRIME B760M-F D4 (Intel B760/AMI), 8 GB `2803` — all prior `2803` reports were 16 GB. ### Independent corroboration: X99 + CSM-on → Code 12 (upstream community reproduction of the #88/#61 findings)

Source: [Zagitta/gpu-unlock issue #28 comments](https://github.com/Zagitta/gpu-unlock/issues/28) (user 3615074213, 2026-10-31). Jingsha X99-8D3 (AMI 5.11) + Windows 11: **with CSM on, the unlock transaction is fully green but Windows lands Code 12 / 0xC0000018; with CSM off, the driver loads normally** — independently consistent with this repo's [#88](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/88) (A4G/ReBAR not hard prerequisites; CSM off = recommended for the display chain) and [#61](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/61) (Code 12 law: handoff console-ownership chain failing on both counts → Code 12, independent of unlock/family/topology). ## Community no-USB tool records (unofficial, not endorsed)

§1.4 is absolute for project deliverables (decision record in [#73](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/73)): this project does not ship resident-boot-entry installers and provides no official tutorials. The community approaches below are recorded for existence only — unofficial, not endorsed, no compatibility promised; the risk model of a resident boot entry (automatic firmware-transaction replay on every power-up, and a black screen requiring recovery media or the firmware menu if the chain-load fails) is borne by the user:

- [#33 reporter's scripts](https://github.com/chungtair/rtx4060ti-auto-unlock): 300 MB FAT32 partition on a data drive + a `{fwbootmgr}` firmware boot entry, tested on AD106/MSI B550 (row #33 above; note the B550 ignores the boot order written by Windows — you must set Boot Option #1 manually in BIOS).
- [#29 reporter's ESP experiment](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/29) (tested on GA102/Z490, row #29 above): putting the unlocker on the system ESP is feasible, but capacity is a hard constraint — this machine's ESP was only 100 MB (69.1 MiB initially free) while the ga102 payload needs 80.7 MiB (`fwimage_ga102.bin` alone is 80.3 MiB), leaving it 11.6 MiB short of the full package; the reporter resized with a PE stick + diskgenius, rebuilt the boot chain and got it working, also self-shortening the confirmation countdown to 2 s. Consistent with the #73 downstream tool's "reject ESP" design trade-off: the ESP route has no headroom for payload size, and a dedicated partition is more robust.
- [bailu974's Secure Boot practice record](https://github.com/bailu974/nv-uefi-unlocker-on-SecureBoot): stuck-key patch (EC-synthesised `Ctrl+C`) + Insyde per-file trust + a full ESP-resident `Boot0000`-rewrite deployment script set (with backup/rollback), the whole process written up in six docs; **zero NVIDIA firmware assets in the repo** (correct discipline - assets generated with the official maker for personal use); the details are folded into the FAQ's [route C](faq.en.md#secureboot), [internal-ESP variant](faq.en.md#secureboot) and [ghost keys](faq.en.md#ghost-key) sections
- [The #73 proposer's downstream tool](https://github.com/Catnip202X/nv-uefi-unlocker/tree/downstream): `downstream/install-partition.ps1`, install/uninstall on a dedicated FAT32 partition (per-file SHA-256 verification, manifest written before the boot entry, rejects ESP/removable disks/partial asset sets, `-AllowArmed` gates auto-confirmation). The author honestly states the script was never actually executed — the first real run is the test.
- [The D#229 reporter's internal ESP-typed partition deployment](https://github.com/physicsdolphin/nv-uefi-unlocker/discussions/229) (field-tested on the AD107 / MECHREVO Kuangshi G16, see the D#229 row above): after `shrink`-ing a 1 GiB FAT32 partition off the data disk, **change the partition type GUID to ESP** (diskpart `set id=c12a7328-f81f-11d2-ba4b-00a0c93ec93b`) and the AMI firmware **auto-registers** a `UEFI OS` boot entry on the next cold start — no `bcdedit /copy`, no manual NVRAM writes, system ESP untouched (one step fewer than #33's bcdedit route, and unlike bailu974's it does not rewrite `Boot0000` — the least invasive form of this lineage); **parsing discipline: whether the firmware enumerated the partition is judged from `bcdedit /enum firmware`, not the BIOS dropdown** (the dropdown only shows device-class placeholders and leads to a false "not enumerated"); put a copy of `BOOTX64.EFI` at the volume root and in `\EFI\BOOT\` (the #142 lesson) plus the armed marker for auto-run at boot. The resident risk model is the reader's own, per the section header.
