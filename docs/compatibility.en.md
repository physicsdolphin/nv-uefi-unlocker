This tool covers GTX 16 through RTX 40 series. The matrix separates family support from device-level evidence and lists known platform limitations.

## Series support

| Series | Support | Prerequisite |
| --- | --- | --- |
| GTX 16 | Asset-level full-family support (tu11x die-keyed assets in tree); per-card field records accumulating; OS-side driver acceptance is the open question - four exclusion axes cleared (FEAT domain / canary / SS rate / WPR2 shape), suspicion narrowed to SEC2 residue (fwsec-only discriminator vehicle staged, #286) | GSP-RM |
| RTX 20 | Fully compatible, laptops and desktops; the 0x91 family is root-caused and fixed | GSP-RM; restart after enabling it |
| RTX 30 GA10x | Fully compatible | No Turing Windows registry prerequisite |
| RTX 40 | Fully compatible on laptops and desktops | GPU powered and initialized at entry |
| Pre-Turing / GA100 / RTX 50 | Unsupported | — |

<a id="routing"></a>

## Routing and evidence

Routing uses chip families. Same-family IDs share Booter/payload assets; a routed ID does not imply an individual hardware test.

| Tier | Meaning |
| --- | --- |
| ✅ | This tool has hardware evidence; EFI-only or OS-side-only results are marked explicitly |
| 🟢 | Upstream or community silicon evidence for the same chain; not individual EFI verification |
| 🟡 | Code path exists; complete hardware verification pending |
| ❌ | Unsupported |

| Family | PCI device-ID ranges | Assets |
| --- | --- | --- |
| Turing · RTX 20 (TU102/104/106; TITAN/Quadro RTX, CMP 40/50HX) | `0x1e02..=0x1f80` | `tu10x` |
| Turing · GTX 16 (TU116/117; CMP 30HX) | `0x1f81..=0x1fff`, `0x2182..=0x21d1` | `tu11x` (die-keyed assets, the #151 route) |
| Ampere GA10x | `0x2200..=0x22ff`, `0x2400..=0x25ff` | `ga102` |
| Ada | `0x2600..=0x28ff` | `ad102` |

Mobile, workstation, CMP and modded devices within a supported family use that family’s route. GA100 (A100 `0x20b0` / `0x20c2`, A30 `0x20f1`), Hopper and Blackwell have no supported route. Unlisted same-family IDs inherit the family evidence tier.

## Verified status and exceptions

<a id="device-1"></a>

### AD107 · 4060 Laptop 28e0

Full-chain unlock and Windows verification pass, including an independent platform reproduction of in-OS state and Tensor gains. [#119](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/119) is a third independent datapoint (same PHN16-71 line, **BIOS V1.20**, driver 617.42): a three-run ablation shows **hybrid-mode entry reads BAR0/MMIO as all `0xffffffff` while NVIDIA-GPU-Only makes the sweep 13/13 readable** (display-mode matrix, Insyde V1.20 sample); TX fully green, FP16 +49.4% / BF16 +56.9% (group spread suggests a thermal limit - cooling under review); Secure Boot and BitLocker disabled for the run, restored and verified after. Sources: [report](ada28e0-uefi-report.md), [#63](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/63), [#119](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/119).

**A Lenovo read-only contrast point ([#251](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/251), 2026-11-16/19)**: the Y7000P IRH8 / BIOS `M2CN40WW` `28e0` read-only round (dGPU-direct, FEAT sweep 13/13, `FEAT_PLM=0xffffff8f`, selectors `0x22352016`/`0x2`, `READOUT_1=0x00410080`) plus both **zero-write gates** on rc4 (30 s timeout ABORT, `tx-dry-run.txt` skip); real TX was deliberately deferred by the reporter (only main machine), so this is **not an unlock sample**.

**Hybrid vs dGPU-direct mode contrast ([D#284](https://github.com/physicsdolphin/nv-uefi-unlocker/discussions/284), 2026-11-22)**: a Legion Y9000P IRX9 (83DF, i9-14900HX) gives a same-machine, same-stick pair on the `28e0` where **the MUX state decides whether the unlock survives**: in hybrid (Optimus) mode HANDOFF was fully green (`SS0=0x88888888`/`SS1=0x8`/canary intact/both D0) yet Windows read `NOT_UNLOCKED`, canary cleared and the SS pair gone (`PLM=0xffffff8f`, SS0 `0x40361076`, SS1 `6`) - and since `EnableRuntimePowerManagement=0` was set, the card and root port were both D0 at sample time and the RTD3 policy was 0, driver RTD3 is excluded and the shape points at a **post-handoff full-domain reset / platform power sequencing** (FAQ [loss taxonomy](faq.en.md#relock) row 1). Switching to dGPU-direct (the iGPU vanishes from the device list) held: `UNLOCKED`, canary intact, `0x88888888`/`0x8`. Performance: 8192³ FP16 25.56→42.08 (1.65x)/BF16 1.62x/TF32 1.74x/FP8 1.79x, three controls flat; 120 s sustained last-30 s 18.38→38.03 (**2.07x**) at 94.4→102.1 W with the median SM clock *falling* (2520→2160 MHz) = efficiency, not a bigger power budget. Boundaries: the locked baseline is hybrid and the unlocked numbers are dGPU-direct, so the mode variable is not isolated (the three unclamped paths not moving suggests the mode itself is worth only a few percent); d2d +46% is self-flagged as untrustworthy; S3 clearing the unlock matches the existing taxonomy.
