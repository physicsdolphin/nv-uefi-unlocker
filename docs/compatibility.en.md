## Series support

| Series | Support | Prerequisite |
| --- | --- | --- |
| GTX 16 | Theoretically compatible; hardware verification pending | GSP-RM |
| RTX 20 | Fully compatible; the 0x91 family is root-caused and fixed, recent-driver reset under investigation | GSP-RM; restart after enabling it |
| RTX 30 GA10x | Fully compatible | No Turing Windows registry prerequisite |
| RTX 40 | Fully compatible on laptops and desktops | GPU powered and initialized at entry |
| Pre-Turing / GA100 / RTX 50 | Unsupported | — |

<a id="routing"></a>

## Routing and evidence

Routing uses chip families. Same-family IDs share Booter/payload assets; a routed ID does not imply an individual hardware test.

| Tier | Meaning |
| --- | --- |
| ✅ | This tool has hardware evidence; EFI-only or OS-side-only results are marked explicitly |
| 🟢 | Upstream or community silicon evidence for the same chain; not individual EFI verification |
| 🟡 | Code path exists; complete hardware verification pending |
| ❌ | Unsupported |

| Family | PCI device-ID ranges | Assets |
| --- | --- | --- |
| Turing | `0x1e02..=0x1fff`, `0x2182..=0x21d1` | `tu10x` |
| Ampere GA10x | `0x2200..=0x22ff`, `0x2400..=0x25ff` | `ga102` |
| Ada | `0x2600..=0x28ff` | `ad102` |

Mobile, workstation, CMP and modded devices within a supported family use that family’s route. GA100 (A100 `0x20b0` / `0x20c2`, A30 `0x20f1`), Hopper and Blackwell have no supported route. Unlisted same-family IDs inherit the family evidence tier.

### AD107 · 4060 Laptop 28e0

Full-chain unlock and Windows verification pass, including an independent platform reproduction of in-OS state and Tensor gains. [#119](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/119) is a third independent datapoint (same PHN16-71 line, **BIOS V1.20**, driver 617.42): a three-run ablation shows **hybrid-mode entry reads BAR0/MMIO as all `0xffffffff` while NVIDIA-GPU-Only makes the sweep 13/13 readable** (display-mode matrix, Insyde V1.20 sample); TX fully green, FP16 +49.4% / BF16 +56.9% (group spread suggests a thermal limit - cooling under review); Secure Boot and BitLocker disabled for the run, restored and verified after. Sources: [report](ada28e0-uefi-report.md), [#63](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/63), [#119](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/119).

### GA102 · 3090 Ti 2203 / 3090 2204 / 3080 2206 / 3080 12GB 220a / 3080 LHR 2216 / 3080 Ti 2208 / CMP 90HX 220d etc. (0x2200..=0x223f routed)

`2206` / `2216` pass firmware read-backs and Windows performance verification; `2208` (3080 Ti, EVGA FTW3) measured via a [bilibili opus](https://www.bilibili.com/opus/1266090375307591685): cold-boot-no-USB vs `--reapply` same-script A/B — TF32 +73%/FP16 +67%/BF16 +68%, FP32 control flat, official dense achievement 91–98%; other same-family devices are fully routed. Gains depend on power and workload.

`2206` **B350M-A closed out** ([#133](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/133), 2026-11-03, first AMD 300-series datapoint): the C1 shape (hang in both recursive and non-recursive reconnect) was eliminated by the single variable **CSM Disabled** (`ConnectController` returning in 1.45 s); the before/after `pnputil` resource table pins the CSM module's legacy-VGA claim (IO 3B0-3BB / 3C0-3DF + the A0000-BFFFF framebuffer disappear with CSM off, everything else unchanged — the reference evidence form for "CSM claimed it" across the C1 family). Performance (4096³ GEMM F32 acc, median of 15): FP16/BF16 53.5→101.5 (**+90%**), TF32 27→51.9 (+92%), FP32 flat; corroborates #29's MSI Z490 UNIFY 2206 datapoint.

Platform notes (2026-11-03): `2204` (3090) on ASUS X570 hangs at ConnectController after a successful transaction ([#106](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/106); `tx-reconnect-nonrecursive.txt` does not help, the `no-reconnect.txt` path awaits a follow-up log — same shape as the #52/#35/#61 reconnect-hang family; the CSM-compat remedy is tracked in #107). A 3080 20GB modded card on Z390P shows GSP devinit resetting SS0/SS1 back to factory ([#109](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/109); 30-series cards must **not** enable the Turing GSP registry switch — retest with it off; the report also adds Z390P/AMI to the platform list).

First virtualization data point (2026-11-03): `2216` unlocked end to end inside a Proxmox VE 9 / QEMU q35 / OVMF Windows 11 guest with VFIO passthrough, v2.1.9 unchanged ([#135](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/135); FP16 57.85→91.64 / BF16 58.72→96.98 TFLOPS, GEMM output hashes identical to stock, FP32 control flat). The unlock survives a guest reboot and a VM stop/start (the host's joint `.0`+`.1` hot reset), loader reports `EALREADY` — FLR/hot reset ≠ power cycle; the AON domain persists and only a host power cycle is expected to clear it (this host keeps D3cold disabled to hold the rails). Entry-state fact: a card fully driven by the Windows driver in the previous session still entered the loader with PLM closed (0xffffff8f) — host-side agents cannot move FEAT_OVR_PLM, again. VM practice notes: a passthrough GPU usually has no pre-OS keyboard, so the armed marker (`\i_know_what_i_am_doing.txt`) is the practical default; `x-vga=1` + `vga: none` with the card as the only console needs no `no-reconnect.txt`; the host pinned BAR1 to 256 MiB via an enumeration-time CTRL write while PSTRAPS still decodes 64 MiB (`override_en=0`) — straps = power-on default, live window = enumeration-time write, confirmed again; `FEAT_READOUT_1` factory value mirrors PSTRAPS SET0 (0x00400080) and drops to 0 when unlocked — the readout tracks the effective clamp. Also recorded: overclocking works unchanged inside the guest (+90/+1000 MHz, 1905 MHz cap, 370 W applied by a Windows task ~2 min after boot, i.e. after the loader; 600 s soak ≈89 TFLOPS, median ~300 W at 1350 MHz, power-capped 100% of the time) — clock/power control paths work in a VFIO-passthrough guest, and the requested-370 W vs delivered-~300 W gap corroborates the per-rail board-limit hypothesis.

2026-11-02 pci.ids correction: the old "3070 Ti 2205" entry was wrong - the shipping 3070 Ti is GA104 `2482`, while `2205` / `2207` are cancelled GA102 ES SKUs (RTX 3080 Ti 20GB / a GA102 3070 Ti), now listed explicitly as ES above. The runtime span is narrowed to `0x2200..=0x223f` accordingly (the old 0x22..ff tail holds no GA102 cores - only HD-audio functions, Tegra/THOR/GB10 ARM blocks and H100 NVSwitch). ES/cancelled SKUs (`222b` 3090 ES, `222f` 3080 11/12GB ES, `2205`, `2207`) are GA102 cores inside the span and run as-is for anyone holding one; tier 🟢 (upstream silicon) until a first hardware report. Sources: [#29](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/29), [#15](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/15).

### GA104 · 3070 2484–248c / 3060 Ti 2489 etc. (whole 0x24xx range routed)

`2489` passes full-chain and Windows verification on AMD, including a cross-vendor VBIOS. A Thunderbolt eGPU `2484` passes EFI execution but loses the unlock in Windows. **The Thunderbolt loss is concluded to be the downstream bus reset the OS connection manager (Windows `Usb4HostRouter` / Linux `thunderbolt` module) performs when it takes the tunnel over** - not the card, not the enclosure, not the firmware: in the same shape on a desktop TB4 + AD102 the canary survived the handoff, POST-to-OS and even a booted Linux, and was cleared only in the seconds of the module takeover; the gate is closed by that reset, before any driver binds, so `--reapply` is structurally dead and the only out is suppressing the reset (Linux `thunderbolt.host_reset=0`, unverified). **A second, non-Thunderbolt form was added on 2026-11-04 (X570 AORUS ULTRA desktop, single display GPU, driver 617.42): the EFI chain is fully green (PLM flip in ~148 ms, selector read-backs, post-FLR AON survival, `plm_open=true`), but after Windows boots the SS pair is no longer intact (`0x0`/`0x0`) and the gate is back at `0xffffff8f`** — the SS pair is lost (not a mere gate closure), same family as #99/#109; `0x0` is also this card's post-reset baseline (see the cold-value table), so zeroing and factory-restore cannot be separated locally. The writer is undetermined (driver-init reset/re-derivation vs platform firmware, plus one unexcluded item of our own: the v2.1.10 native-GOP rebuild tail), so a safe-mode cut and an event-log capture were issued; the classification will be back-filled ([#164](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/164)). Other same-family devices are fully routed. Sources: [#11](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/11), [#54](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/54), [Thunderbolt limits](faq.en.md#thunderbolt).

**`25a0` (3050 Ti Laptop, GA107M 4GB, AMD Ryzen 6800H hybrid) = first GA107M EFI-path data point** ([#148](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/148), 2026-11-03, Linux Mint 22.3 / 595.71.05): v2.1.9 chain fully green (PLM flip, SS write + read-back, post-FLR AON survival, `PMC_BOOT_0=0xb77000a1`), but **the Linux driver actively re-derives the FEAT block at init** — after `modprobe nvidia`, PLM returns to `0xffffff8f` and SS0/SS1 to factory variants. Three mechanism markers: (1) RTD3 was off (`DynamicPowerManagement: 0`) → not the [#9](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/9) idle-power-down mechanism; (2) **both GSP-RM and legacy init re-derive, programming different bits** (SS0 delta from factory: GSP `0x00400100` / legacy `0x00400000`; FEAT+0x08 `0x82`↔`0x83`) → active programming in both paths, not a "state not preserved" side effect; (3) post-FLR AON survival → not an FLR wipe (FLR doesn't clear, power loss clears, init re-derivation is a third kind). Benchmarks showed no gain (the panel moved to the dGPU shares the 80 W TGP; FP32 drops by the same 0.92× ratio, confirming power budget rather than partial unlock). **Attribution boundary (N=1, not generalized)**: the differing bit patterns prove the writer is the **kernel driver init itself** (an EC/firmware writer would not vary with the init mode); but "Linux drivers always re-derive" does not hold — same-family `25ad` **persisted on Windows** (PLM open, [#142](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/142)), and the #82/#126 family established the relock as topology/MUX/EC-conditioned (#126's writer fired before driver load, on a GC6/D3cold wake). Three unsevered variables: OS codebase (Linux nvidia.ko vs Windows nvlddmkm), driver version (595.71.05 is very new; #103 survived on 580.142), and MUX/EC platform state (the persistence test ran in dGPU-MUX mode). Severing experiments, ranked: (1) driver-version A/B on the same laptop (550/570 LTS vs 595), (2) Linux desktop GA10x, (3) hybrid-mode persistence after a cold-shutdown enumeration test, (4) post-modprobe settle-timing probe. `--reapply` remains structurally impossible behind a closed gate (host writes dropped; SEC2-mediated in-OS rewriting belongs to the upstream kmod lineage, out of this tool's UEFI scope). The report also adds a hybrid-laptop criterion: **panel owner / MUX position decides enumeration** (Hybrid + warm reboot = empty slot, refuse-to-guess zero writes; after `supergfxctl -m AsusMuxDgpu` the same stick ran the full chain), now folded into the display-mode axis. Source: [#148](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/148).

### TU106 · RTX 2070 1f07 / 2060 Super 1f06 / 2060 12GB 1f03 / 2070 Laptop 1f14 (rest of the TU106 family in the device table)

`1f07` / `1f06` / `1f03` / `1f14` pass full-chain and in-OS verification. `1f03` (2060 12GB) failed the FWSEC stage on v2.1.6 with an EXCI error; six controlled experiment rounds in [issue #89](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/89) pinned it to a 4 GiB-boundary staging DMA reachability problem (same shape as #74), and it now runs with the **FWSEC VRAM staging + BridgeMaster guard fixes** (2026-11-01). `1f14` (2070 Laptop, barebone CNH5L, dGPU-direct) is a 0x91-family fix verification (v2.1.3+, [#16](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/16)). **Same-die mining note**: CMP 40HX is TU106 silicon (`1f0b`, the field vehicle of the Pry paper and PZH1gdmu/CMP40HX-Unlock — the lineage source of this whole transaction family), routable within the span. Windows requires GSP-RM and a restart. Handoff relocks FEAT PLM while preserving the override values; the unlock path skips FLR. For nonstandard VRAM capacities, check the usable-memory decode in the log. **Open**: Windows-side `nvlddmkm` PF FLR resets during driver init ([#99](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/99); both early datapoints, 1f06 and 1f07, ran 621.01 / GSP 620.67.01, and the 630.20 sample still lacks an official source). The relock is not tied to a driver version - classify by the SS pair: `1f07` only re-closes the gate with SS intact, `1f06` is zeroed.

**In-OS safe "reset" (2026-11-04, verified on the project's Z170 TU106 bench)**: Device Manager **disable → re-enable** of the GPU **does not drop the unlock** (ssdiag still `UNLOCKED` afterwards) — the PnP-disable path unloads the driver, re-arbitrates resources and parks the device in D3, but does **not** perform a function-level reset, so the AON-domain FEAT PLM/SS pair is untouched. Two uses: (1) an in-OS self-remedy for display-arbitration problems such as Code 12 — disable/re-enable forces Windows to reassign resources; the bench recovered exactly this way from a post-handoff Code 12 under CSM-on; (2) a contrast against #99's PF FLR — **a PnP disable ≠ an FLR**: the former is safe, the latter drops the unlock (Turing). GA10x boundary untested: the #126/#109 devinit-relock family runs through the RTD3-wake/driver-init paths, and whether a PnP disable/re-enable touches GA10x devinit has no data yet — if a GA10x machine shows `--reapply` REFUSED after such a cycle, classify it under the relock family; that does not invalidate this datapoint.

**Platform/firmware as a dimension (observation mode, 2026-11-03)**: the suspect variable has moved from the SKU to the platform side, and it is **not laptop-only**. Laptops: the same `1f15`, the same driver 617.42 / GSP 615.78.05 and byte-identical assets stay `UNLOCKED` on an X99 discrete-attach board — 6 samples identical over 10 min 15 s with zero `nvlddmkm` events and no convergence between the two PLM registers (`GFW_PLM` stays stock, so the init path never touches the FEAT block) — while the same die back on a MUXless Optimus laptop relocks at the bind boundary ([#82](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/82)), and the shape reproduces on Ampere after a GC6/D3cold wake, before driver bind ([#126](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/126)). Desktops: a `2206` modded 20GB card on 2017–2019-era AMI boards (Z390P [#109](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/109), PRIME B350M-A [#133](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/133), TUF B450M-PRO [#134](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/134)) closes the FEAT gate during driver init and pushes SS back to factory, while **the same card, VBIOS and SUBSYS on a current-generation board (B650, CSM off) keeps the gate open at ×1.84–1.97 throughput over a 9-minute-order measurement**. Disabling the iGPU on #109 does not stop the relock, so the iGPU itself is not the trigger. One more card in another form: an X570 AORUS ULTRA desktop `2484` on 617.42 zeroes the SS pair and closes the gate after Windows boots ([#164](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/164); CSM state unreported, and this is the "wiped" shape rather than pushed-back-to-factory). **The driver version is not the discriminator**: under the same 621.01 the project's own `1f07` merely relocks with SS intact (`0x88888888`/`0x8`, readout 0 — still unlocked), [#99](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/99)'s `1f06` is zeroed to `0x0`, and this case is re-derived to factory — three outcomes on one driver. Each report therefore has to be classified by the **SS pair**: a closed gate only costs the `--reapply` escape, a wiped SS pair is the actual loss. **None of this is paired with a desktop replay control yet — recorded as an observation, not a conclusion.**

Mechanistically: **whether a relock happens depends on who re-runs devinit before bind on the platform side** — on laptops that is the MUX controller vendor's and the EC vendor's behaviour design; on old desktop firmware it is the CSM-era firmware's legacy-VGA/init path. All of these re-run devinit whenever their own logic decides a reset is due (pushing the FEAT block back to factory), and none is under driver control. Corollaries to verify: for laptop users "upgrade the driver" only swaps one relock path for another, it is not a fix (617.42 survives on a direct-attach board); on the desktop side the driver version no longer has to be gated first. The `#99` PF FLR is recorded as another observed shape of the same family (reset form), bucketed apart from the relock form.

Sources: [TU106 report](evidence/m3-tu106/host-and-final-result.md), [#12](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/12), [#89](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/89), [#16](https://github.com/physicsdolphin/nv-uefi-unlocker/issues/16), [GSP prerequisite](faq.en.md#turing).
